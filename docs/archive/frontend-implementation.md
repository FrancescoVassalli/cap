# Consumer Assistance Program Frontend Implementation Guide

## 1. Purpose

Build a mobile-first React frontend for the Colorado Consumer Health Initiative's Consumer Assistance Program (CAP).

The frontend has two purposes:

1. Explain the CAP program and help consumers understand whether they should seek assistance.
2. Replace the current basic request form with a guided, accessible intake experience that collects the information CAP staff need to begin a case.

The application should preserve the approachable, nonprofit/community-oriented character of the existing website while substantially improving:

* clarity
* mobile usability
* accessibility
* form completion
* error handling
* visual hierarchy
* maintainability
* separation between presentation and business logic

The current CAP site states that assistance is free, that CAP does not directly pay medical bills, and that a team member generally follows up within five business days, although higher inquiry volume can make responses take longer. The new application should make those expectations clear rather than hiding them in secondary content.

---

# 2. Technical direction

## 2.1 Stack

Use:

* React
* TypeScript
* Vite
* Tailwind CSS
* React Router
* Formik
* Yup or another small schema-validation library
* Vitest
* React Testing Library
* Playwright for end-to-end/mobile accessibility testing

Use Vite because the frontend is intended to be a static application deployed to S3. Vite's production build produces a bundle suitable for static hosting, with `vite build` generating the deployable `dist` directory.

Use Formik for the intake form. Formik provides field/form state, touched state, validation, submission state, and support for multi-step forms without requiring a global state manager.

Use the current Tailwind installation approach rather than the deprecated Play CDN approach; Tailwind explicitly describes the Play CDN as development-only.

### Important architectural rule

**Components are dumb.**

A presentational component should receive:

```tsx
<Input
  label="Email"
  value={value}
  error={error}
  onChange={onChange}
/>
```

It should not know:

* where the data came from
* what an intake is
* how the API works
* how ZIP lookup works
* what step the user is on
* how an email is generated
* how documents are uploaded

Business behavior belongs in hooks/services.

For example:

```tsx
const { currentStep, next, back, canContinue } = useIntakeNavigation(...);
const { lookupZip, isLoading } = useZipLookup();
const { submit, status } = useIntakeSubmission();
```

This will make the eventual transition from a static prototype to a real backend substantially easier.

# 4. Routes

The application should use these public routes.

| Route          | Purpose                          |
| -------------- | -------------------------------- |
| `/how-we-help` | Explain CAP                      |
| `/intake`      | Intake landing/instructions page |
| `/intake/:id`  | Individual intake form           |
| `*`            | Not-found page                   |

The original specification uses `/instake/id`; this should be implemented as `/intake/:id`.

The `:id` value should be generated by the browser when a user starts an intake.

Example:

```ts
const intakeId = crypto.randomUUID();
navigate(`/intake/${intakeId}`);
```

The ID should contain no personal information.

Do not use:

```text
/intake/john-smith
/intake/123-main-street
/intake/john@example.com
```

Use:

```text
/intake/8f4a7e74-2c9e-4d4c-a49d-9a4c2e8d4f31
```

The URL is allowed to identify the intake session, but nothing sensitive should be encoded into it.

# 5. Static hosting architecture

The intended initial architecture is:

```text
User
  │
  ▼
CloudFront / HTTPS
  │
  ▼
S3
  │
  ▼
React SPA
```

Eventually:

```text
User
  │
  ▼
CloudFront
  │
  ├──────────────► S3 static assets
  │
  └──────────────► API
                       │
                       ├── CRM
                       ├── Email
                       └── S3 document storage
```

React Router can be used with static hosting, but the hosting layer must return the SPA entry point when users directly navigate to client-side routes. React Router documents static hosting as a supported deployment pattern.

For an S3/CloudFront deployment, configure appropriate fallback/error handling so `/how-we-help` and `/intake/:id` do not become S3 404s when directly loaded. AWS documents custom error responses through CloudFront for this purpose.

Prefer:

```text
CloudFront -> private S3 bucket
```

rather than exposing the application bucket directly to the internet.

# 6. Visual design system

The visual design should feel like an evolution of the existing CCHI/CAP site rather than a completely unrelated startup application.

Current branding should be reused where possible, including the CAP logo and existing imagery. The existing CAP page already uses the CAP logo, team imagery, funder logos, and nonprofit branding.

## 6.1 Colors

Define these as design tokens:

```css
--color-primary: #01599A;
--color-secondary: #7AABDB;
--color-highlight: #FEC524;
```

Use them approximately as:

* Primary: headers, major buttons, links, active states
* Secondary: informational backgrounds, secondary actions, subtle accents
* Highlight: calls to action and attention areas

Do not use yellow/highlight as the only indicator of errors or success.

Define semantic tokens as well:

```text
--color-text
--color-muted
--color-border
--color-background
--color-surface
--color-error
--color-success
--color-focus
```

The semantic layer prevents the application from coupling every component directly to brand colors.

---

#### Define loading/error/empty/success states

Every data-dependent action should have:

idle
loading
success
error

For the intake process, specifically define:

submission failure
network interruption
duplicate submission
server validation failure
session expiration
successful submission

The success screen should tell the user what happens next, rather than simply saying "Thank you."

That maps nicely to the real CAP workflow, where staff subsequently contact the consumer and may request authorization and documents

# 7. Typography

Use a highly readable sans-serif font.

Prioritize:

* readability over visual novelty
* large body text
* generous line height
* clear heading hierarchy

Recommended baseline:

```text
body: 16px+
line-height: 1.5
input text: 16px
small text: never below approximately 14px
```

Avoid overly compressed typography.

This population may include users who are:

* stressed
* tired
* on a phone
* unfamiliar with insurance terminology
* using assistive technology
* dealing with a large medical bill

The interface should therefore feel calm rather than dense.

# 13. Intake architecture

The entire intake should be implemented as **one Formik form**.

```tsx
<Formik
  initialValues={initialValues}
  validationSchema={schema}
  onSubmit={handleSubmit}
>
  <IntakeForm />
</Formik>
```

There should not be five independent forms.

Instead:

```text
Formik
  └── IntakeForm
      ├── Step 1
      ├── Step 2
      ├── Step 3
      ├── Step 4
      └── Submission
```

Formik's support for validation and multi-step forms makes this structure appropriate.

---

# 14. Intake data model

Use a typed object.

```ts
export interface IntakeFormValues {
  zipCode: string;

  language: "en" | "es";

  firstName: string;
  lastName: string;

  email: string;
  phone?: string;

  address1: string;
  address2?: string;
  city: string;
  state: "CO";
  postalCode: string;

  documents: IntakeDocument[];
}
```

Do not put API-specific fields directly into the Formik state unless necessary.

For example, avoid:

```ts
{
  apiUploadToken: "...",
  crmCaseId: "...",
}
```

Keep those concerns in services/state outside the presentation model.

# 15. Step 1 — ZIP code

The user can skip ZIP code.

UI:

```text
What ZIP code do you live in?

[ 80203 ]

We'll use this to help fill in your city and state.

[ Skip this step ]
```

The field should accept only five-digit US ZIP codes.

Validation:

```text
empty      -> valid
123        -> invalid
80203      -> valid
80203-1234 -> optionally normalize or reject
```

Prefer accepting standard five-digit ZIP codes initially.

## ZIP lookup

A static ZIP dataset can live in:

```text
src/data/zipCodes.json
```

Example:

```json
{
  "80203": {
    "city": "Denver",
    "state": "CO"
  },
  "80521": {
    "city": "Fort Collins",
    "state": "CO"
  }
}
```

However, ZIP code should **not** be treated as a source of a street address.

A ZIP code can determine a postal locality such as city/state, but it cannot determine:

```text
123 Main Street
```

Therefore the UX should say:

```text
ZIP code
  ↓
City/state may be filled automatically
  ↓
User enters street address
```

When an unknown ZIP is entered:

```text
We couldn't find that ZIP code. You can continue and enter your address manually.
```

This is better than blocking intake.

# 18. Step 4 — Documents

The document step should clearly explain why documents are useful.

Example:

```text
Documents

You can upload documents that may help our team understand your situation.

Examples:
- medical bills
- explanation of benefits
- insurance letters
- claim denial letters
- other relevant documents

You can skip this step and provide documents later.
```

Because documents may contain sensitive health information, the UI must not falsely suggest that ordinary public cloud storage is being used.

## Future production architecture

The intended flow should be:

```text
Frontend
   │
   ├── POST /intakes/{id}/upload-url
   │
   ▼
Backend
   │
   └── creates short-lived S3 presigned URL
           │
           ▼
Frontend
   │
   └── PUT file directly to S3
```

AWS documents presigned URLs specifically for allowing clients to upload to S3 without giving those clients AWS credentials.

Do **not** put AWS access keys in the React application.

Do not make the sensitive document bucket public.

Recommended future S3 key:

```text
intakes/{uuid}/documents/{random-document-id}
```

Do not use the original filename as the security boundary.

Example:

```text
intakes/8f4a.../documents/51b0....
```

rather than:

```text
intakes/john-smith/medical-bill.pdf
```

# 19. Prototype document behavior

The first static frontend may not have a backend.

Therefore create an abstraction:

```ts
interface DocumentUploadService {
  upload(file: File, intakeId: string): Promise<UploadedDocument>;
}
```

Production implementation:

```text
PresignedS3DocumentUploadService
```

Prototype implementation:

```text
LocalDocumentUploadService
```

The prototype can:

* validate the file
* display the selected file
* calculate size
* display upload status

but should not pretend that a sensitive document has been securely stored when it has not.

Until the backend exists, the safest prototype behavior is to make document upload a UI-only capability or explicitly route it through a separately approved secure backend.

# 20. File validation

The frontend should validate:

* file size
* allowed file types
* duplicate selection
* empty/corrupt selection where detectable

Suggested initial types:

```text
PDF
JPG/JPEG
PNG
```

Suggested maximum:

```text
10 MB per file
```

and a total intake limit such as:

```text
50 MB
```

These values should be configuration rather than hard-coded throughout components.

```ts
const documentConfig = {
  maxFileSizeBytes: 10 * 1024 * 1024,
  maxTotalSizeBytes: 50 * 1024 * 1024,
  acceptedTypes: [...]
};
```

Do not trust frontend validation as a security control. The eventual backend must validate all of these again.

# 23. Back-button behavior

The browser Back button should behave predictably.

When navigating between steps, use either:

```text
location-independent internal step state
```

or controlled routing.

For the first implementation, keep the steps inside the same `/intake/:id` route and track:

```ts
currentStep: number
```

This avoids putting form state into the URL.

The browser Back button should not unexpectedly leave the intake.

If the user attempts to leave with unsaved information, consider a lightweight browser-level warning only where technically appropriate. Do not create an aggressive modal on every navigation.

# 24. Intake persistence

The specification says:

> The intake should not persist.

Therefore:

* no localStorage
* no sessionStorage
* no IndexedDB
* no URL-encoded form state
* no cookies containing form data
* no browser persistence of PHI

A refresh should lose the current in-memory form.

This is intentional.

The eventual backend can provide controlled persistence after the security model has been designed.

# 25. Submission architecture

Do not couple the form component directly to email.

Instead:

```ts
interface IntakeSubmissionService {
  submit(
    intakeId: string,
    intake: IntakeFormValues
  ): Promise<SubmissionResult>;
}
```

The form only knows:

```ts
await submissionService.submit(...)
```

The implementation can change later.

Initial prototype:

```text
EmailSubmissionService
```

Future production:

```text
ApiSubmissionService
```

---

# 26. Important security decision: email

The requirement that the prototype "generate an email" should be treated as a transitional mechanism, not the long-term architecture.

Do not put sensitive information into a `mailto:` URL.

Do not put documents into an email URL.

Do not send healthcare information through an unreviewed third-party email service merely because it is easy to integrate.

A `mailto:` implementation may be acceptable as a development/demo mechanism only when the content is intentionally limited and the limitations are clearly understood.

For production, the expected architecture should be:

```text
React
  ↓
HTTPS API
  ↓
validated intake
  ↓
secure storage / CRM
  ↓
notification email
```

The notification email should say something like:

```text
New CAP intake received.

Intake ID: 8f4a...

A new consumer request is available in the case management system.
```

It should not unnecessarily contain the consumer's complete medical narrative or document contents.

# 27. Submission states

Every submission-related operation must have explicit state.

```ts
type SubmissionStatus =
  | "idle"
  | "submitting"
  | "success"
  | "error";
```

The UI should never silently fail.

## Idle

```text
Submit Request
```

## Submitting

```text
Submitting your request...
```

Disable repeated submission:

```text
button disabled
```

## Success

Show a dedicated success screen.

Example:

```text
Request received

Thank you for contacting the Consumer Assistance Program.

A member of our team will review your request and contact you by phone or email. CAP generally responds within five business days, although it may take longer when we receive a high volume of requests.

Please keep any relevant medical bills, insurance letters, explanations of benefits, and claim information available in case our team needs additional information.

Your reference number is:

8F4A-7E74
```

The current CAP process says that staff contact the consumer, may send an authorization form, may request documents securely, and then work with the consumer toward resolution. The new success screen should set that expectation.

# 28. Submission failure

If submission fails:

```text
We couldn't submit your request.

Your information was not submitted successfully.

Please check your internet connection and try again.
```

Buttons:

```text
[ Try Again ]
[ Contact CAP ]
```

Do not display raw exceptions.

Bad:

```text
TypeError: Failed to fetch
```

Good:

```text
We couldn't connect to the service.
```

Log technical details only to an approved development/operations system, never to the browser console in production when those details could contain sensitive data.

---

# 29. Network interruption

The UI should distinguish a likely network failure from ordinary validation failure.

Example:

```text
Your connection was interrupted.

We couldn't finish submitting your request.
Please reconnect and try again.
```

Do not automatically retry submission without a mechanism preventing duplicate case creation.

---

# 30. Duplicate submission

The submit button should be disabled immediately once submission begins.

Backend/API should eventually provide an idempotency key.

For example:

```text
Idempotency-Key: <intake-id>
```

The frontend can generate it from the intake ID.

This allows:

```text
user clicks submit
   ↓
request fails after server received it
   ↓
user clicks again
   ↓
backend recognizes same submission
   ↓
duplicate case is not created
```

This should be implemented in the API once the backend exists.

---

# 31. Server validation errors

When the backend exists, support errors such as:

```json
{
  "errors": {
    "email": "Please enter a valid email address.",
    "postalCode": "Please enter a valid ZIP code."
  }
}
```

Map these into Formik.

```ts
setFieldError("email", apiError.errors.email);
```

Also support a general error:

```text
We couldn't submit your request because some information needs attention.
Please review the highlighted fields.
```

Move keyboard focus to the error summary when appropriate.

---

# 32. Session expiration

Because the initial intake does not persist, session expiration should be uncommon.

Once backend persistence exists, the API may return:

```text
401 / 403
```

The frontend should display:

```text
This request is no longer active.

For your privacy, this intake session has expired.
Please start a new request.
```

Never expose backend session tokens in the URL.

---

# 33. Form validation

Validation should be defined outside components.

Example:

```ts
const intakeSchema = yup.object({
  zipCode: yup
    .string()
    .matches(/^\d{5}$/, "Enter a 5-digit ZIP code")
    .nullable(),

  language: yup
    .mixed<"en" | "es">()
    .oneOf(["en", "es"])
    .required(),

  firstName: yup.string().trim().required("Enter your first name"),

  lastName: yup.string().trim().required("Enter your last name"),

  email: yup
    .string()
    .trim()
    .email("Enter a valid email address")
    .required("Enter your email address"),

  address1: yup
    .string()
    .trim()
    .required("Enter your street address"),
});
```

Step validation should be selective.

When leaving Step 1, validate Step 1.

When leaving Step 2, validate Step 2.

When submitting, validate the complete form.

Do not force the user to fix unrelated future-step errors.

# 35. Accessibility

Target **WCAG 2.2 AA**.

WCAG 2.2 specifically covers keyboard focus, labels/headings, focus visibility, input modalities, and target sizing among many other requirements.

Required:

### Keyboard

Every interactive element must be usable with:

```text
Tab
Shift+Tab
Enter
Space
Arrow keys where appropriate
Escape where appropriate
```

### Focus

Every focusable element must have a visible focus state.

Do not remove:

```css
outline: none;
```

without replacing it with an equivalent accessible focus indicator.

### Labels

Every form field must have an actual associated label.

Use:

```html
<label htmlFor="email">Email address</label>
<input id="email" ... />
```

not placeholder-only labeling.

### Errors

Each error must be associated with its input.

Example:

```html
<input
  aria-invalid="true"
  aria-describedby="email-error"
/>

<p id="email-error">
  Enter a valid email address.
</p>
```

### Required fields

Do not rely on an asterisk alone.

At minimum:

```text
First name *
```

plus:

```html
aria-required="true"
```

where appropriate.

### Color

Never communicate:

```text
valid
invalid
selected

progress
```

using color alone.

### Headings

## Mobile layout

```text

one-column forms
```

All input fields should be full width on mobile.

unless there is sufficient width.

The preferred mobile presentation is:

Target approximately 44–48px minimum interactive size.

# 42. Localization

Build the application so that English and Spanish content can coexist from the beginning.

Use:

```ts

```

and content dictionaries:

```ts
const content = {
  en: {...},
  es: {...}

```

Bad:


This will avoid awkward grammar and make future professional translation easier.

# 44. ZIP data implementation

Create an explicit service:

```ts
interface ZipLocation {
  city: string;
  state: string;
}

export interface ZipService {
  lookup(zip: string): ZipLocation | null;
}
```

Then:

```ts
const location = zipService.lookup(zip);

if (location) {
  setFieldValue("city", location.city);
  setFieldValue("state", location.state);
}
```

Do not have the component directly import and manipulate the raw JSON database.

# 45. Separation between frontend and backend

The frontend must not assume the eventual backend shape.

Create an application-level interface.

```ts
interface SubmissionService {
  submit(input: SubmitIntakeInput): Promise<SubmitIntakeResult>;
}
```

Then create:

```text
MockSubmissionService
EmailSubmissionService
ApiSubmissionService
```

This is one of the highest-value architectural decisions in this project.

It allows the static prototype to be implemented now without rewriting the intake when the backend arrives.

# 46. Security requirements

Because the application handles potentially sensitive insurance and health information, security should be treated as a design requirement rather than an API implementation detail.

## Must not happen

Do not place sensitive information in:

* URL query parameters
* URL paths
* analytics events
* browser console logs
* error-tracking breadcrumbs
* client-side telemetry
* localStorage
* sessionStorage

Avoid third-party scripts unless explicitly reviewed.

## HTTPS

Production traffic must be HTTPS-only.

Redirect HTTP to HTTPS.

## Secrets

Never place:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
API private keys
JWT signing secrets
```

in frontend environment variables.

Anything shipped in a React bundle is effectively public.

## Analytics

Analytics should initially be minimized.

Do not send events such as:

```text
claim_denied = true
bill_amount = 14000
insurance_company = ...
diagnosis = ...
```

A safe event may be:

```text
intake_started
intake_step_viewed
intake_completed
```

even then, verify that identifiers and form contents are not attached.

For the first release, no analytics is a perfectly reasonable default.

# 47. Third-party scripts

Default policy:

```text
No third-party scripts on intake pages.
```

This includes:

* advertising scripts
* session-recording tools
* arbitrary analytics
* heatmaps
* marketing trackers

These tools can unintentionally capture form inputs or URLs.

If a third-party service is eventually required, it needs an explicit privacy/security review before being added.

# 48. Document security

Production documents should eventually be stored in a private S3 bucket.

Use:

```text
private bucket
+
short-lived presigned uploads
+
server-controlled object keys
```

AWS specifically supports presigned URLs as a way to permit time-limited S3 access without distributing AWS credentials to the uploading client.

Do not expose:

```text
https://bucket.s3.amazonaws.com/medical-bill.pdf
```

as a permanent public URL.

# 59. Final implementation principle

The most important architectural distinction is:

```text
Components = presentation
Hooks      = interaction/state behavior
Services   = external operations
Content    = copy
Types      = contracts
Validation = business rules
```

The intake should therefore look conceptually like:

```text
                   React UI
                      │
             ┌────────┴────────┐
             │                 │
        Formik state       UI hooks
             │                 │
             └────────┬────────┘
                      │
                Form validation
                      │
                      ▼
             SubmissionService
                      │
          ┌───────────┼───────────┐
          │           │           │
       prototype    email       future API
          │                       │
          │                       ├── CRM
          │                       ├── S3
          │                       └── notifications
          │
       temporary
       transition
```

This keeps the initial application small and static while preserving a clean path to the eventual CRM/backend architecture.

The frontend should be designed as a **trustworthy intake experience first and a web form second**. For this audience, reducing uncertainty, preventing accidental data exposure, making the form usable on a phone, and clearly explaining what happens after submission are core product requirements rather than polish.
